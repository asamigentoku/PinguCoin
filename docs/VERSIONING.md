# バージョン管理

3つの「バージョン」を、それぞれ管理しています。

| 何の | どう管理するか | 使うもの |
| --- | --- | --- |
| **リリース**(システム全体) | セマンティックバージョニング。git のタグ `v1.2.3` | `script/release.sh`、`release.yml`、`pkg/version` |
| **API**(外部とサービス間のインターフェース) | URL の `/api/v1`、gRPC のパッケージ `orcan.v1`。互換性を壊さない | `buf breaking`、`X-API-Version` |
| **DB スキーマ** | 番号付きの SQL ファイル。適用した番号を DB に記録 | `pkg/dbmigrate`、`services/*/migrations/` |

---

## 1. リリースのバージョン

### 番号の決め方(セマンティックバージョニング)

`vMAJOR.MINOR.PATCH`(例: `v1.4.2`)。システム全体(3つのサービスとフロントエンド)で、1つの番号です。

| 上げる | とき | 例 |
| --- | --- | --- |
| MAJOR | 互換性を壊す変更(API の `v2` を出す、利用者に影響する大きな変更) | `v1.4.2` → `v2.0.0` |
| MINOR | 後方互換の、機能の追加 | `v1.4.2` → `v1.5.0` |
| PATCH | バグ修正、内部の改善(見た目の仕様が変わらない) | `v1.4.2` → `v1.4.3` |

- プレリリースは `v1.5.0-rc.1` のように付けます。GitHub では、プレリリースとして公開されます。
- 最初の公開前は `v0.x.y`(`v0.1.0` から)。MINOR が、互換性を壊してもよい(1.0 より前の約束)。
- 候補は、`bash script/release.sh next` で、直近のタグから表示されます。

### リリースの手順

```text
main で開発 ──▶ タグを付ける ──▶ GitHub Release が自動で作られる ──▶ (出したいとき) production ブランチへ ──▶ 本番へデプロイ
```

1. `main` が、出したい状態になっていることを確認する(CI が通っている)。
2. タグを付けて push する。

   ```bash
   bash script/release.sh v1.5.0 --dry-run   # 確認だけ
   bash script/release.sh v1.5.0 --push      # タグを付けて push
   ```

   スクリプトは、`main` にいる・作業ツリーがきれい・`origin/main` と同じ・同じタグが無い、を確認します。

3. GitHub Actions の **Release**(`release.yml`)が、タグの形式と、コミットが `main` に入っていることを確認し、テストを通して、**GitHub Release** を作ります。変更の一覧は、マージされた PR から、**ラベル別に自動で**まとめられます(`.github/release.yml`)。PR には、次のラベルを付けてください。

   | ラベル | リリースノートの見出し |
   | --- | --- |
   | `breaking-change` | 互換性を壊す変更 |
   | `feature` / `enhancement` | 新機能 |
   | `bug` | バグ修正 |
   | `security` | セキュリティ |
   | `infrastructure` / `ci` | インフラ・デプロイ |
   | `documentation` | ドキュメント |
   | (なし) | その他の変更 |
   | `ignore-for-release` | 載せない(Dependabot の PR も、載せない) |

4. 本番に出すときは、`main` から `production` ブランチへ、プルリクエストでマージします([DEPLOYMENT.md](DEPLOYMENT.md))。

リリース(タグ)と、本番へのデプロイは、**別の操作**です。タグを付けても、本番は変わりません。

### 動いているバージョンの確かめ方

バージョンは、ビルドのときに、バイナリに埋め込まれます(`pkg/version`。`go build -ldflags "-X ...Version=v1.5.0"`。Dockerfile の `VERSION` / `COMMIT` / `BUILD_TIME`)。

| どこで | どう見るか |
| --- | --- |
| ログ | すべてのログの `version` 属性([LOGGING.md](LOGGING.md))。起動時のログに、コミットとビルド時刻も出る |
| pingu-api | `GET /version` → `{"service":"pingu-api","version":"v1.5.0","commit":"…","build_time":"…","go_version":"…","api":"v1"}` |
| イメージ | ラベル `org.opencontainers.image.version`(`docker inspect`)。イメージのタグは、git の SHA |
| GitHub | リリースのページ(タグ・変更の一覧) |

バージョンは、`git describe --tags` で求めます。タグの直後は `v1.5.0`、その後にコミットが続くと `v1.5.0-3-g1a2b3c4`(タグから 3 コミット後)、タグが無い間は、コミットの短い SHA になります。埋め込まれていない(`go run` など)ときは `dev` です。

### 前のバージョンに戻す

- **アプリ**: 前の成功したコミットで **Production: Deploy** を再実行します(イメージは、SHA でタグ付けされていて、上書きされないので、そのまま使えます)。
- **DB**: 前のバージョンのアプリは、新しいスキーマの DB でも、起動できます(新しいマイグレーションを、知らないだけ。下の「3」)。ただし、新しいバージョンで**列を削除・名前変更**していた場合は、古いアプリは動きません。そのため、列の削除・名前変更は、2段階(下の「3」の「安全な変更の手順」)で行います。

## 2. API のバージョン

### HTTP(GraphQL / REST)

- URL に、バージョンを含めます: `/api/v1/graphql`、`/api/v1/orders`、`/api/v1/points`。レスポンスにも、`X-API-Version: v1` を付けます。
- **同じバージョンの中では、互換性を保ちます。**

  | OK(後方互換) | NG(`v2` が必要) |
  | --- | --- |
  | レスポンスに、項目を足す | 項目・エンドポイント・GraphQL のフィールドを、削除・名前変更する |
  | 新しいエンドポイント・フィールドを足す | 項目の型や意味を変える |
  | 省略可能な入力を足す | 必須の入力を足す |

- GraphQL は、フィールドを**削除せず**、`@deprecated` を付けて、案内します(`schema.graphqls`)。
- 互換性を壊す変更が必要になったら、`/api/v2` を新しく出し、`v1` は、告知してから、期間を置いて止めます(最低でも、利用者が移行できる期間。目安は 3 か月)。

### gRPC(サービス間)

- protobuf のパッケージ名に、バージョンを含めます: `orcan.v1`、`payment.v1`(`services/*/proto/`)。
- **同じパッケージの中では、後方互換**です。フィールドの追加・RPC の追加は OK。フィールドや RPC の削除・番号の変更・型の変更は NG(新しいパッケージ `orcan.v2` にする)。
- **CI が、自動で確かめます。** プルリクエストで、`buf breaking`(`ci.yml` の proto ジョブ)が、宛先ブランチと比べて、互換性を壊す変更があると、失敗します。

## 3. DB スキーマのバージョン

DB の変更は、**番号付きの SQL ファイル**で管理します(`services/<service>/migrations/NNNNNN_説明.sql`)。以前の `AutoMigrate`(起動のたびに、モデルから差分を自動で当てる)は、使いません。「いつ、何を変えたか」が Git の履歴に残り、本番でも、適用された内容が、はっきり分かるためです。

### 仕組み(`pkg/dbmigrate`)

- 起動時に、**まだ適用していないファイルだけ**を、番号順に適用します。適用した番号は、DB の記録のテーブルに残ります(番号・名前・チェックサム・時刻)。テーブルは、**サービスごとに別**です(`orcan_schema_migrations` / `payment_schema_migrations` / `pingu_schema_migrations`)。開発・staging では、3つのサービスが1つのデータベースを共有するので、記録を共有すると、各サービスの「番号 1」がぶつかるためです。
- 1つのファイルは、**1つのトランザクション**です。途中で失敗したら、そのファイルの変更は全部取り消され、記録も残りません(次の起動で、最初からやり直し)。
- 適用したファイルを**書き換えると**、チェックサムが合わず、**起動に失敗します**(適用済みの DB と、新しい DB の、スキーマの食い違いを防ぐため)。
- 前にしか進みません(down のファイルは無い)。間違えたら、直す SQL を、**新しいファイル**で足します。
- 複数の Pod が同時に起動しても、DB のロックで、1つずつ実行します。
- 既存の DB(以前の `AutoMigrate` で作られた)では、番号 1 のファイル(ベースライン = 導入した時点のスキーマ全体)を、実行せずに、適用済みと記録します。

### 変更の足し方

1. 次の番号のファイルを作る(例: `services/payment-api/migrations/000002_add_refund_note.sql`)。

   ```sql
   -- 返金にメモを付けられるようにする。
   ALTER TABLE refunds ADD COLUMN note varchar(50);
   ```

2. 対応するモデル(`internal/model`)も変える。
3. テストを実行する。**`TestMigrationsMatchTheModels`** が、マイグレーションとモデルが一致しているかを確かめます。モデルだけを変えて、マイグレーションを足し忘れると、このテストが失敗します(コードは新しい列を使うのに、本番の DB には無い、という事故を防ぎます)。
4. 適用済みのファイルは、**書き換えません**。

ファイル名は `NNNNNN_説明.sql`(6 桁の連番、1 から、途切れなし)。番号の重複や、途切れがあると、起動(とテスト)が失敗します。

### 安全な変更の手順(古いアプリが動くように)

デプロイの間(古い Pod と新しい Pod が、同時に動く)と、ロールバックのときは、**古いアプリが、新しいスキーマの DB を使います**。そのため、次のように、2段階で行います。

| 変更 | 手順 |
| --- | --- |
| 列を追加 | 1回で OK(NULL 許可か、デフォルト値を付ける)。古いアプリは、その列を知らないだけ |
| 列を削除 | ① アプリが、その列を使わないようにして、リリース → ② 次のリリースで、`DROP COLUMN` のマイグレーション |
| 列の名前変更 | ① 新しい列を追加して、両方に書く → ② 読む先を切り替える → ③ 古い列を削除(それぞれ、別のリリース) |
| `NOT NULL` を足す | ① デフォルト値つきで、列を追加 → ② 値を埋める → ③ アプリが必ず値を入れるようにして、リリース → ④ `NOT NULL` を足す |
| 大きなテーブルのインデックス | `CREATE INDEX CONCURRENTLY` は、トランザクションの中で使えないので、別途、手動で行う(まず相談) |

### 状態の確認

```sql
SELECT version, name, applied_at FROM orcan_schema_migrations ORDER BY version;  -- payment_ / pingu_ も同じ
```
